# WC-2026-09-30-db-typed-503 — a fired database ceiling is a typed 503

- **Date:** 2026-09-30 (audit 2026-09-26, PERF-11).
- **Decision:** none (a defect fix with a wire effect; the defaults are unchanged — the on-by-default flip, PERF-11 C4, is a separate later entry).
- **Doors:** every door whose statements run through `src/core/db/postgres.ts` `sql`
  (the pooled and in-transaction lanes).
- **Shape before:** a statement stopped by `DB_STATEMENT_TIMEOUT_MS` (SQLSTATE 57014) and
  a caller that waited out `DB_POOL_ACQUIRE_TIMEOUT_MS` both reached the converter as an
  untyped error → 500 `internal.unexpected`, indistinguishable from an engine bug. Both
  keys defaulted to `0` (off / wait forever), `DEDALO_SLOW_QUERY_MS` to `0`.
- **Shape after:**
  - 57014 AT OR PAST the lane's ceiling → 503 `db.statement_timeout` (`unavailable`,
    public, `retryable: false`, label `error_db_statement_timeout`). An operator's
    `pg_cancel_backend`, the update engine's abort cancel, a cancel before the ceiling,
    and any 57014 on a reserved connection stay raw (unchanged).
  - The acquire timeout → 503 `db.pool_exhausted` (`unavailable`, public,
    `retryable: true`, label `error_db_pool_exhausted`). `sql.reserve()` now takes a gate
    slot, so reserved connections can no longer exhaust the pool behind the gate (the
    next pooled query used to hang).
  - Lane, ceiling and pool numbers ride only in operator `coordinates`; no `details`.
  - Defaults unchanged (`0` for all three); new `DB_MAINTENANCE_POOL_MAX` 2.
  - A session `SET` / `RESET` / `DISCARD` in ANY statement of the text (a multi-statement
    `SELECT 1; SET …` included), or a literal `set_config(…, false)`, issued through the
    pooled or transaction lane is refused (`internal.invariant`) before it is sent — it
    would outlive the caller on a pooled connection (the WC-055 leak class).
  - A Bun `sql` member that takes a connection outside the doors (`begin`, `transaction`,
    `savepoint`, `file`, `listen`, `close`, …) is refused (`internal.invariant`). No
    engine caller used one.
  - `dd_area_maintenance_api::widget_request`: only the actions a widget declares
    maintenance (`unboundedActions` — store rebuilds, VACUUM/REINDEX, bulk transforms,
    imports) run on the maintenance pool, unbounded; every other action keeps the request
    ceiling. `dataframe_control.run_check`/`run_fix`: a batch that runs past what is left
    of the per-table/total budget is cut (the budget becomes a statement bound) and its
    table reports `status: 'budget_exhausted'` in `coverage` (existing enum value; reason
    text `batch at id > <n> ran past the <ms>ms left of the budgets …`); a batch cut by the
    pool ceiling stays `status: 'error'`, and an `error` reason now names the failure's
    code or SQLSTATE (`batch at id > <n> failed (<code>; see the server log): …`) instead of
    the raw driver message, which goes to the server log (SEC-18).
- **Amends:** WC-055 (maintenance no longer clears the GUC with a session `SET`/`RESET`;
  it runs on a maintenance pool born with `statement_timeout = 0`).
- **Client:** a 503 `db.*` must render as a transient toast, never a relogin/reload
  (`client` `error_policy` check — follow-up).
- **Gate reconciliation:** no parity fixture recorded a timeout or an exhausted pool; no
  fixture edit. Gates: `test/unit/statement_ceiling_scope_native.test.ts` (typed legs per
  lane, raw legs, the recorder, the acquire gate incl. reserve, the session-SET refusal),
  `test/unit/maintenance_door_unbounded_native.test.ts` (declared actions unbounded, an
  undeclared one neither lifted nor starved, the dataframe budget cut),
  `test/unit/config_census_tripwire.test.ts` (the maintenance pool key, config docs current),
  `test/unit/statement_timeout_exemption.test.ts`.

## Addendum 2026-09-30 — the maintenance lock-wait bound, and the optimize sweep

Review of PERF-11 (same day).

- **Lock-wait bound.** Lifting the statement ceiling had also lifted the only bound
  on a lock WAIT: a declared action queued for ACCESS EXCLUSIVE (a store rebuild's
  `TRUNCATE`, an `ALTER`) behind a long reader held every later reader of that table
  queued behind it, for as long as the long reader ran. The transactional maintenance
  pool is now born with `lock_timeout = 5s` (`MAINTENANCE_LOCK_TIMEOUT`; the
  non-transactional CONCURRENTLY/VACUUM lane keeps none).
  - **Shape before:** a declared `dd_area_maintenance_api::widget_request` action
    waited for a lock without limit.
  - **Shape after:** the wait gives up at 5 s (SQLSTATE 55P03; that transaction rolls
    back). One the action lets escape → 503 `db.lock_timeout` (`unavailable`, public,
    `retryable: true`, label `error_db_lock_timeout`; `coordinates`
    `{ lane: 'maintenance', lock_timeout }`, operator-only; the SQLSTATE rides as
    `cause`). One the action catches keeps that action's own report — e.g.
    `backfill_search_stores` adds `<store> backfill: <driver text>` to `errors[]` and
    leaves that store's old rows. Undeclared actions: unchanged (request pool, no
    lock bound). The data-update engine's default `SET LOCAL lock_timeout` is the same
    constant (value unchanged, `5s`).
  - **Gate:** `test/unit/maintenance_door_unbounded_native.test.ts` (a later reader gets
    through while the long reader still holds; the escaping wait is `db.lock_timeout`
    with SQLSTATE 55P03).
- **`database_info.optimize_tables` sweep** (landed with the entry, recorded here). A
  NON-dry-run optimize first runs `DROP INDEX CONCURRENTLY` on every invalid index of
  the named tables that PostgreSQL named `<index>_ccnew[N]` / `<index>_ccold[N]`,
  skipping any table with an index build in progress (`pg_stat_progress_create_index`).
  A failed drop adds `SWEEP failed for invalid index <name> (see server log)` to
  `errors[]` and never makes the action fail; dropped names go only to the server
  log. A dry run (`dry_run: true`) sweeps nothing. Gate:
  `test/unit/optimize_concurrent_leftover_native.test.ts`.
